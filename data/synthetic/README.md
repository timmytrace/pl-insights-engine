# Synthetic match dataset

Football-realistic event data generated by `MatchSimulator` from a single integer seed per
match. No real match data, clubs or players are used: every club and player is fictional.

## What's here

| File | Contents |
|---|---|
| `matches.csv` | One row per match for seeds 1–100: score, xG, shots, passes, pass accuracy, possession, PPDA, event count, duration |
| `events/seed-N.csv` | Every event of matches 1–5 (≈2,000 rows each) |
| `../sample/seed-7/` | Match 7 as JSON: `match.json` (metadata, squads) and `events.jsonl` (events **with tracking frames**) |

Everything regenerates byte-for-byte from its seed, so you can produce as many matches as you
need instead of downloading them:

```bash
cd backend && dotnet run --project src/Studio.Cli -c Release -- dataset --seeds 1-1000 --events 1-50 --out ../data/synthetic
```

```bash
cd backend && dotnet run --project src/Studio.Cli -c Release -- generate --seed 42 --out ../data/sample/seed-42
```

## Event schema (`events/seed-N.csv`)

Coordinates are metres on a 105 × 68 pitch in a fixed frame where the **home team always attacks
towards x = 105** (no half-time switch).

| Column | Meaning |
|---|---|
| `id`, `seq` | Event id (`SYN-<seed>-<seq>`) and sequence number |
| `t` | Elapsed seconds of play, monotonic across both halves |
| `clock`, `period`, `minute` | Match clock in seconds (second half starts at 2700), half, broadcast minute |
| `type` | `kickoff`, `pass`, `carry`, `shot`, `tackle`, `interception`, `pressure`, `foul`, `possession_change`, `sprint`, `substitution`, `period_end` |
| `team`, `player_id` | Acting side (`home`/`away`) and player (`H01`–`H16`, `A01`–`A16`; see squads in `match.json`) |
| `x`, `y`, `end_x`, `end_y` | Start and end location |
| `outcome` | Per type, e.g. pass `complete`/`intercepted`/`incomplete`/`out`; shot `goal`/`saved`/`off_target`/`blocked`; possession change reason |
| `receiver_id` | Intended receiver of a pass |
| `under_pressure` | 1 if the actor was being pressed |
| `possession` | Possession sequence number |
| `ball_speed_kmh`, `player_speed_kmh`, `distance_m` | Measured quantities, as a tracking system would supply them |
| `body_part`, `xg` | Shot body part and expected goals |

The JSONL form adds `players`: on every on-ball event, all 22 player positions, like a tracking feed.

## How it's generated

A possession-chain model: the ball carrier is pressed (or not), then shoots, carries or passes.
Pass success comes from the same pass-difficulty formula the insight engine reports, and shot
outcomes from the same xG model, so the metrics and the data agree. Team styles drift during a
match (one side switches to a high press after the hour, fatigue sets in, trailing teams go
direct), which gives the insight engine real stories to discover from the data alone.

## Known deviations

- **Too many goals.** About 3.8 per match against ≈2.7–2.9 in real top-flight football, and
  0–0 draws are rare (1%). The simulator creates too many close-range chances, so xG per shot
  (≈0.17) is higher than real (≈0.11). Fine for demonstrating insight and narrative; not for
  calibrating betting or scouting models.
- **Positional model, not physics.** Tracking frames come from a team-shape model that shifts
  with the ball. Players move between events rather than continuously.
- **No set-piece detail.** Corners and free kicks restart play but aren't modelled as distinct
  routines.
